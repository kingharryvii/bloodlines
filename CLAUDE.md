# Bloodlines — Project Codex

A custom race/bloodline system for a private Forge 1.20.1 modpack. This file is a reference for
both future Claude Code sessions and for you — it captures the state of the mod, the architecture,
and the non-obvious lessons learned building it, so none of that has to be rediscovered.

## What this mod is

Players pick a **bloodline** (race) once; it grants:
- Attribute modifiers (health, speed, damage, knockback resist, luck, attack speed) — `RaceStats.java`
- Innate passive effects (night vision, fire resist, water breathing, slow falling, jump boost) — `RaceEffects.java`
- One active ability with a cooldown — `RaceAbility.java` (10s duration, 45s cooldown, server-validated)
- Real cosmetics where it fits the race: tails, head accessories, wings, body size

Race selection and ability use are **server-authoritative** — the client never decides these on its
own, it just renders based on server-synced state (`ClientRaceCache`).

## Architecture

**Capability**: `IPlayerRace`/`PlayerRace`/`PlayerRaceProvider`/`PlayerRaceCapability` — standard
Forge capability, one race + a set of unlocked races per player, serialized to NBT.

**Server → client sync**: `SyncPlayerRacePacket`, sent on login (`PlayerRaceEvents.onPlayerLogin`),
on death/respawn (`onPlayerClone`), and when a new observer starts tracking a player
(`onStartTracking`). The client caches it in `ClientRaceCache` (a simple `Map<entityId, Race>`) —
**every** client-side race check (rendering layers, the Mixin) reads from this cache, never from the
capability directly (the capability is server-only in practice for gating logic).

**Rendering layers** (all in `client/render/`, registered in `BloodlinesClientSetup.addLayers`):
- `TailLayer` — Merfolk + Beastkin tails
- `HeadAccessoryLayer` — halo, horns, elf ears, cat ears
- `FaeWingsLayer` — Fae's elytra-based wings

Angelkin/Demonkin wings are **not** rendered by Bloodlines at all — see `IcarusWingHooks`.

**Mixin**: exactly one, `MerfolkSwimRotationMixin`, targeting `PlayerRenderer.setupRotations`.
Deliberately kept isolated — see "The Merfolk tail" below for why it exists and what it does.

## The Merfolk tail (the hard part)

This took most of the session. Current, confirmed-working state:

- **Model**: `TailModel.createMerfolkLayer()` — a direct port of the real MerMod mod's own
  `TailBuilder`/`TailLayerDefinitions.getDefault()` (7 tapering segments + 1 fin + side-fin quads per
  segment), traced from MerMod's actual decompiled/reference source, not approximated.
- **Texture**: `merfolk_tail.png` is a real community reskin (currently Aino's Mermod Mermaid Tail
  Retexture), used **completely unresized** at its native 96×122. Minecraft doesn't require a
  texture's pixel dimensions to match a model's declared `texWidth`/`texHeight` — UV coordinates are
  baked as *fractions* of the declared grid, so a higher-res texture just stretches to fit. An
  earlier attempt manually resized the source art down to a literal 48×64 PNG before using it — that
  extra step was unnecessary and actively broke the fin's texture.
- **Attachment**: `anchorToBody=true` — the tail's root attaches via
  `getParentModel().body.translateAndRotate(poseStack)` (matching MerMod's own technique exactly)
  plus `TORSO_HEIGHT / 16F` (0.75 blocks). The `/16` is not optional — `ModelPart.translateAndRotate()`
  divides its x/y/z by 16 internally (confirmed by decompiling the real method), because `PoseStack`
  operates in true block-scale while `PartPose` offsets are written in "pixel" units. A raw
  `poseStack.translate(0F, 12F, ...)` (forgetting the `/16`) puts something 12 *blocks* away, not
  0.75 — this was a real, shipped bug (tail invisible) diagnosed by decompiling `ModelPart` directly.
- **Swim rotation**: `MerfolkSwimRotationMixin` injects into `PlayerRenderer.setupRotations` (after
  the `super.setupRotations()` call inside the `swimAmount > 0` branch, `ordinal=1`), replacing
  vanilla's swim-tilt with a plain rotation (`Axis.XP.rotationDegrees(angle)`, no pivot-wrap trick).
  A pure rotation always fixes the coordinate origin — that's why this keeps the tail's attachment
  point locked at the pelvis regardless of swim angle. Two earlier approaches both failed for the
  same underlying reason (introducing a translation component that let the origin drift):
  1. A `TailLayer`-side "cancel vanilla's rotation and reapply it around the hip" approach — fine at
     shallow angles, broke down at steep dive angles.
  2. A Mixin using the textbook "translate-to-pivot / rotate / translate-back" identity — correct for
     transforming *one point*, but wrong as a `PoseStack` prefix, because it shifts where the
     *origin* lands by `hip - R(hip)` (angle-dependent), and `TailLayer`'s own translate always
     starts from that (now-moving) origin.
- **Rendering**: `RenderType.entityTranslucent(texture)`, not `entityCutoutNoCull`. The real MerMod
  source renders its tail with `armorTranslucentCull`. Cutout does a binary alpha test with no
  blending; several of these community reskins use soft/graduated alpha for shading, which a cutout
  test turns into visible noise instead of a smooth fade.

If any of this regresses, re-verify each piece independently before touching the others — this
system broke in confusing, compounding ways more than once when multiple things changed at once.

## Beastkin tail — known follow-up

Beastkin's tail (`BloodlinesClientSetup`, the `TailLayer` constructor call for `Race.BEASTKIN`) still
uses `anchorToBody=false`, i.e. the *old* `entity.getBbHeight() * heightFraction` positioning that
Merfolk used to have — not the corrected `anchorToBody=true` + `TORSO_HEIGHT/16F` technique. It
wasn't switched over during the Merfolk fix to keep that test isolated to one variable at a time (see
git history / conversation for the reasoning). If Beastkin's tail base ever looks like it's drifting
with pose changes, this is almost certainly why — same bug class as the Merfolk one, just not yet
carried over.

## Abandoned: new Mixin injections never execute, project-wide, confirmed root cause never found

Any *new* Mixin class added to this project — anything beyond the original `MerfolkSwimRotationMixin`,
which has been in place since before this was first noticed and still demonstrably works — passes
every static check (annotation processor accepts the target method, the built jar's refmap resolves
it to a real obfuscated name, `require = 1` raises no error, the game boots fine) but never
demonstrably executes at runtime. This was chased across two separate features in two separate
sessions before being conclusively proven project-wide, not feature-specific:

- A minimal isolation test (`Minecraft#tick()`, the simplest possible non-generic target, handler body
  unconditionally throwing an exception) never crashed the game — not once, not even at the main menu,
  across a fully clean `gradlew clean build` with no Gradle daemon reused between builds.
- The same test jar, dropped into a real, non-dev, production Minecraft client (not the ForgeGradle
  `runClient` userdev environment) — still no crash. Rules out a dev-environment-specific quirk too.
- A differential logging test showed even the *known-working* `MerfolkSwimRotationMixin`'s own log
  line never appeared in console output either — so "no log line" was never reliable evidence on its
  own; this project's logging setup just doesn't surface Mixin-handler output, working or not. Only a
  hard crash (an unmissable, unambiguous signal) or an actual observed gameplay effect can prove a new
  Mixin fires here.

Root cause never found despite exhausting every plausible explanation: config registration (confirmed
correct at every path the runtime actually reads, not just the built jar), refmap staleness, generic
vs. non-generic target classes, four structurally different injector techniques (`@Inject` with erased
types, `@Inject` with the target's own generics replicated to match a real shipped Fabric mod's
equivalent fix, `@Redirect`, and MixinExtras' `@WrapWithCondition` matching the real MerMod mod's own
technique for the same problem) - **all four fixes** were themselves verified correct via decompile and
even matched against real, working mods' actual source, not guessed.

- **Fae flying-limb-freeze** (hold a flying Fae's arms/legs in a neutral pose instead of playing the
  walk animation): verified via direct bytecode disassembly that the real call chain reaches
  `PlayerModel.setupAnim()`. Abandoned — see git history around the removal commit for the full
  diagnostic trail if this gets revisited.
- **Merfolk leggings/boots showing through the tail** (`HumanoidArmorLayer` renders leggings/boots
  through its own separate `innerModel`/`outerModel` instances, completely independent of the base
  `PlayerModel` legs `BloodlinesClientEvents#onRenderPlayerPre` already hides): all four techniques
  above were tried specifically against `HumanoidArmorLayer#renderArmorPiece()`/`#render()`, including
  the MixinExtras dependency (added, then removed again once it also failed - nothing in this project
  needs it). Abandoned — leggings/boots visibly show through the Merfolk tail as a known cosmetic
  limitation. The one untried option left: a reflection-based approach reading `HumanoidArmorLayer`'s
  private `innerModel`/`outerModel` fields directly from `onRenderPlayerPre` — untried because it can't
  work as a simple visibility toggle there (vanilla's own `setPartVisibility()` re-enables those parts
  *after* `Pre` fires, right before each piece draws, so anything set in `Pre` gets overwritten before
  it would take effect); would need clearing the parts' actual geometry instead of their visibility
  flag to survive that, which is a materially different, untried approach.

If this gets revisited, start by re-running the `Minecraft#tick()` crash test above (cheap, ~2 minutes,
completely unambiguous) before spending any real time on a new attempt — if it still doesn't crash,
nothing else has changed about the underlying problem.

## Soft integrations (all optional, mod loads fine without any of them)

- **Pehkui** — entity scaling (`PehkuiIntegration`). Used for Fae (height+width), Dwarf/Troll
  (height, Troll also width).
- **Icarus + Caelus + Curios** — Angelkin/Demonkin flight (`IcarusWingHooks`). No real item is ever
  equipped — `IcarusWingHooks.install()` wraps Icarus's own `IcarusHelper.hasWings`/
  `getEquippedWings` static fields so Icarus believes a winged-race player has wings purely off their
  Bloodlines race. (An earlier version *did* equip a real Curios item, which collided with any other
  mod using the shared "back" slot — backpacks, capes, etc. `IcarusIntegration.removeWings` is
  legacy cleanup for that old system.)

On CurseForge, all three (Pehkui, Icarus, Curios) should be listed as **Optional Dependency**, not
Required — `mods.toml` declares all three `mandatory=false`.

## Non-obvious technical notes worth remembering

- **ModelPart coordinate space**: +Y points down, matching every vanilla humanoid part. `PoseStack`
  itself is true block-scale; `ModelPart`/`PartPose` offsets are "pixel" units (÷16 to get blocks),
  and only `ModelPart.translateAndRotate()` does that division automatically — a raw
  `poseStack.translate()` does not.
- **Box-UV footprint formula** (for hand-computing texture layout): for a box `(w,h,d)` at
  `texOffs(u,v)`: north face UV origin `(u+d, v+d)` size `(w,h)`; south face `(u+2d+w, v+d)` size
  `(w,h)`; total canvas footprint needed: width `2*(w+d)`, height `h+d`.
- **A texture's actual pixel dimensions don't need to match a model's declared `texWidth`/
  `texHeight`** — Minecraft samples UV coordinates as fractions of the declared grid against whatever
  texture is bound. A higher-res replacement texture just works, unresized.
- **`@Inject`'s `require` parameter defaults to -1`** (no minimum match count enforced) — an injector
  that matches zero locations fails **completely silently**, no crash, no log, nothing. Always set
  `require = 1` (or higher) explicitly on any new Mixin injector, the same way this project already
  sets `"required": true` at the mixin-config level — silent failure here cost a lot of debugging
  time once.
- **Verify Mixin refmaps by inspecting the built jar directly**, not just by trusting the build
  succeeded: `unzip -p build/libs/harrys_bloodlines-1.0.0.jar mixins.harrys_bloodlines.refmap.json`
  should show both the injected method and any `@At(target=...)` resolved to real obfuscated names
  (e.g. `m_7523_`), not left as unmapped source names.
- When decompiling vanilla/Forge classes for verification, the bundled Vineflower jar is at
  `~/.gradle/caches/minecraftforge/forgegradle/mavenizer/caches/maven/mcp-tools/org/vineflower/vineflower/1.10.1/vineflower-1.10.1.jar`,
  and the mapped Forge jar to extract classes from is at
  `~/.gradle/caches/forge_gradle/minecraft_user_repo/net/minecraftforge/forge/1.20.1-47.4.10_mapped_official_1.20.1/forge-1.20.1-47.4.10_mapped_official_1.20.1.jar`.
  Extract only the specific `.class` files needed into a temp dir before decompiling — decompiling
  the whole jar is slow and unnecessary.
